# 用一个编排 Skill 调用现有广告混剪能力

## 11 月 18 日已确认的整单实验

业务上遇到的问题是，交给现有流水线的任务常常中途失败，能直接拿去用的整片偏少。实验目标是提高接单后无需人工救场、第一次交给业务审看就能采用的整片比例。仓库记过一批 45 单，首轮 19 单制作完成，人工处理后补跑 15 单，又有 8 单制作完成。这组记录反映了部分制作失败可以恢复，成片能否采用还需看实片。[历史失败与恢复记录](../plans/20261110-overnight-recovery.md)

改造现有 `doubao-jianying-orchestrator`，让 Agent 按任务进度选择已有工具，也让它依据仓库积累的剪辑经验、原句和实际画面决定剪法。常规单可以直接委托现有 Windows 流水线做完整初稿。有明确镜头要求、素材疑点或失败记录时，Agent 也可以先查对应环节，再决定从哪里继续。[主线编排 Skill](https://github.com/starfishwrx/video-editing-automation/blob/de7f0da0854e37fdbaa752ba82a7f64ed8cbe3ee/packages/video-v1.5.3/doubao-jianying-orchestrator/SKILL.md) · [Windows 流水线](../windows-pipeline.md)

| 接单时的情况 | Agent 要做的判断 | 仓库里可直接复用的能力 |
| --- | --- | --- |
| 素材和文案齐全，要出第一稿 | 是否可以直接整单建稿，或先核实某个卖点的素材是否够用 | 素材观察库、`ai_editor` 的整稿选镜、配音与音乐、原生剪映写稿 |
| 审片人指出某句动作重复或卖点不清 | 看实际切片，判断应换入点、换原片还是连相邻句一起改 | 已核验的候选和源窗、指定句补选、连续动作组复核、冻结配音后恢复写稿 |
| 已做出一部分，或质检打回 | 找到最后一个与当前输入相符的结果，决定补看素材、复剪、续做质检或报告缺口 | 任务状态、匹配报告、阶段恢复、独立成片质检和交付验收 |

### 让 Agent 按最佳实践决定剪法

沿用仓库对必须满足的要求、通常值得采用的做法和可选做法的区分。Skill 按当前问题引用已核实的剪辑经验，说明这个做法解决什么观看问题、什么情况下有例外。是否采用建议，由 Agent 看本句、前后镜头和真实可用时长来定。有取舍时，留下所选源窗和一句可从画面核对的理由。[要求用语与适用范围](../../packages/video-v1.5.3/doubao-jianying-orchestrator/references/requirement_levels.md) · [已有选镜经验](../adr/0002-ai-selection.md)

先用“避免重复动作”验证这种分工。相邻两镜都是举起同一包纸、观众第二次看不到新信息时，可以换镜。同一张纸从折叠到展开、恰好到下一句“大张”才露出完整纸幅时，可以保留同一机位，让动作做完。现有机位复核能从实际切片找回切、比较候选并更新选镜方案。实验入口应允许 Agent 同时查看原切片和候选，决定保留、替换或补看。写稿后回读采用的源窗，核对后续自动优化是否改变了这个决定。[机位复核实现](../../packages/video-v1.5.3/doubao-jianying-orchestrator/orchestrator/selection/camera_variety.py)

明确的业务要求仍可直接验。比如卫品吸水实验，同一次实验的倒液、吸收、纸巾接触后提起看结果都要清楚可见。Agent 决定每段是否加速、加到什么程度，三段均无固定倍速上限，由既有实验规则和独立质检核验实际成片。对于“还是四层加厚的”这类口播，Agent 可以先查包装读字观察，再看选中的那一秒是否真能读到“4 层”。[选镜与素材观察](../subsystems/visual-matching.md) · [卫品实验规则](../weipin-experiments.md)

实现优先复用原模块。若某个步骤已经按剪辑偏好自动筛掉候选或改写了结果，就在该步骤提供查看候选和提交选择的入口。指定句补选通过复核后，沿用原有匹配报告和写稿恢复，并复用其余句子和已核验配音。[阶段恢复](../windows-pipeline.md#状态与恢复)

### 首张历史卫品单的整单结果

原流水线在吸水组的配对与时长分配处停住，未生成草稿。实验入口用原单文案、原配音及同款素材观察完成整单，在可编辑草稿上进行了两轮复剪，交出可播放的整片。制作过程的人工选镜和改剪均为零。最后一次复剪只动促销句的入点，其余画面、原生旁白轨、字幕和配乐均已核对。

最终独立质检有七句通过，吸水、纸巾验证两句仍为 `UNCERTIFIED`。同一段画面在前一轮获得通过，成片独立审看也看到了倒液、蓝痕变浅和白纸提起。逐帧模型把部分证据归在相邻阶段，按现有规则继续拦截。可交业务看稿；正式放行与业务首审仍待验证。本次复用已有素材观察且在试验中改过工具，尚无直接成稿率的对照数字。

### 怎么检验直接成片率

先在独立分支用一张历史原单验证。保留原流水线的结果及首次失败位置，Skill 可使用同样的素材、已有观察和配音。核对它接受了哪些原有结果，在哪里提前发现风险或在失败后选择了另一种处理。对有取舍的句子，把工具建议、Agent 的决定和成片实际镜头放在一起看。交付可编辑草稿与可播放整片，记录业务第一次看片是否直接采用，以及实际还须手改哪里。

这张单用于看清机制。后续若衡量比例，取同一批原始订单，包含历史成功与失败单，双方使用相同的预算上限和验收标准。建议的直接成片率为“中途无需人工介入、通过本单约定的质检、业务首看就可采用的整片数 ÷ 分配给该方案的全部订单数”。在成功单中分别记首遍做成和自动补看、补选或恢复后做成。在其余单中分别记出稿前中断、出稿后质检或审片退回及需要人工救回的情况。这样能看出增加的可用整片来自哪一步，也能同时比较耗时、额外调用和人工修剪时间。

## 11 月 17 日原案为何先做单句返工

原案基于 `main` 的 `ae1675e` 与维护包 `packages/video-v1.5.3`。以下保留当时的实验顺序和判断依据。

**值得把业务入口和剪辑决策重构成一个 Skill。先用一条真实返工单验证，再决定正常建稿是否也交给它。** 运营应该能说“第七句没讲清薄透，音轨和其他句子都留着”，让 Agent 自己决定用原片重切、从历史观察找另一个窗口，还是报出缺什么画面。对素材齐全的常规单，Agent 可以直接委托现有整单工具。

如果只想让业务同学在飞书点一下，已有 Windows 调度器可以接本地队列，单做接单桥就能解决启动麻烦。引入 Skill 需要额外证明它能处理不同意图、减少返工。把写稿、计时、恢复、质检也搬进提示词则会让两次运行难以对照，还得重新解决已经有实现的付费重试和交付问题。实验把工程投入放在**编辑决定能否按原样落稿**这个缺口上。

工作区的《项目脚手架与重整》要求盘点已有入口、保兼容并提供可验证的交接。《Skill 写作指南》要求目标、可用资源、输出和验收清楚，把方法选择留给 Agent。按工作区关于依赖、瓶颈和可验证性的原则，原音轨决定可用时长，最终切片决定卖点能否成立。查哪些素材、先修哪一句、要不要另一种剪法，则可以根据这一单决定。

## 如何判断重构有效

每次试单沿用包外的 `work/<队列记录>/report/`、`eval/` 和 `done.json`。另记一张 A/B 对照表，每行一单，含运行和修订标识、变更句、实际源窗、调用数、质检结果、盲评意见与修剪分钟。若没有可用窗口或模型服务不可用，记录原始错误、受影响的句子以及可继续的阶段，作为业务可读的结果。

A 使用当前主线及其已有缓存、局部补选和恢复能力。B 使用实验 Skill。两组使用同一 SKU、文案、素材清单、配音、音乐、工具版本、机器和模型预算。从相同缓存快照各自运行。冷启动和同库第二次运行分开计，A 与 B 互不预热。记录所有任务及失败。盲评只随机展示版本，先看整条，再指出具体句子、支持的卖点和需要手修的分钟数。

| 验证场景 | 判定依据 |
|---|---|
| 正常建稿 | 可打开、编辑并另存原生草稿，口播、字幕和素材对应。正式试单在隔离交付端检查 `INPUT-IDENTITY`、`RUNTIME-IDENTITY`、`DRAFT-PACKAGE`、`VISUAL-QC` 全为 `PASS`。preview 的渲染成功只计预览。 |
| 单句返工与多用途素材 | 用卫品第七句的历史反例。抚摸镜头更清楚仍可能没有卖点信息。照光窗口能支撑薄透相关表达。再换一句文案，从同一长原片检索另一时间窗。要求指出实际支持哪一项、使用哪几秒，并核对组外没被改动。[历史回放](../shot-selling-point-value.md) |
| 失败恢复与缺证据 | 注入选镜限流、写稿后 QC 超时，各从对应阶段恢复，已完成工作不重复付费，重启不重置预算。交换同长度不同内容的音轨，或裁掉实验结果帧，必须阻断。纸品历史样例复用 214 条分析和 13 句配音，三轮改善四处，揉搓仍放不进短句。能准确报缺口也是这类任务的正确结果。[阶段恢复](../subsystems/runtime-and-recovery.md) · [纸品反例](../paper-selection-replay.md) |

**建议先做小样本决策。** 首批取 2 条正常单、3 条定向返工单，外加上述故障样例。逐单记录实际像素模型 HTTP 请求（初看、逐窗复核、最终 QC 分列）、文字请求、TTS 次数、费用、耗时和人工修剪分钟。按商品、原片、源窗、采样和协议核对重复看图次数，另报两组每单的请求差额及费用。先验证热跑对可复用的同一观察没有重复像素请求，换 SKU 或实质性改变观察条件会触发所需的新复核，新草稿保有独立 QC。

试点建议门槛为两条正常单均维持原验收，三个返工样例中至少两个得到剪辑师盲选且减少实际修剪，所有故障样例均阻止误交付。同步比较每单实际费用与耗时，若 B 更贵，列出节省的修剪分钟和增加的费用再决定适用单型。这个规模只决定下一轮试点。若收益只见于返工单，就只开放返工入口。若原生稿与核准计划不符，停止扩大试用。成本或质量收益尚不明确时，保留现行入口，按样例说明哪项没有改善。

**退出与交接。** 实验按任务显式选择。停用试验时停止认领新试单，在途任务按原运行的冻结状态结束或定向恢复，保留 A/B 记录。若试验后决定改变默认生产架构，在采纳变更的同一 PR 补 ADR、索引、RFC、受影响的子系统文档和开发日志，按仓库策略做定向及跨模块回归。[架构决定索引](../adr/README.md) · [测试策略](../test.md)

# ADR 0011 — 按范围验证、并行完整 CI

- 日期：2026-11-09
- 状态：已采纳；实现随本次 PR，生产安装另行授权。

## 背景

固定 main 的离线审计收集到 1831 个唯一用例，约 84% 单项低于 100ms。主要成本来自逻辑单测对假媒体的反复解码、无关宿主进程探测、重复复制整树，以及迭代期间过早启动全量。单个重复源窗测试触发 408 次 FFmpeg 尝试，约 37.5 秒。删除大量快测试不能解决主要问题。

## 选择

1. 先跑对应模块和直接调用方的定向测试，完成独立审阅与修复后，再对最终代码跑一次本地全量。发版候选把这一轮放在最终干净解压包；安装仅验证入口、依赖、库存漂移与必要案例。修改后按实际影响范围补验，不按提交次数重跑。
2. 逻辑测试显式、局部注入固定宿主事实，隔离其不测试的媒体识别入口。保留真实的修复、组装、正式门禁及断言，另用冻结观察覆盖新旧实验策略联动。专门的宿主探测、资源选择和准入测试仍执行原逻辑。
3. 架构负例使用最小合法模块图注入非法依赖，仍保留完整真实树正例、兼容导入及冷启动。常规带音轨抽帧并入 CFR/VFR/非零 PTS 像素对照；旧 FFmpeg 重试和单帧回退独立保留。源码字符串与文档字样改用实际行为覆盖或删除过时断言。
4. CI 的包级和编排器完整 discover 使用两个 Windows / Python 3.11 job 并行，同一事件 SHA，关闭 fail-fast。聚合检查继续名为 `Windows Python 3.11`，总是执行且只接受整个矩阵 success；失败、取消、意外跳过均阻断。
5. PR、main push、手动触发都保留完整回归。暂不实现跨事件结果复用：PR head 不能证明当时实际测试的 merge tree，artifact 自报也不够；API、attempt 与 checkout 证明复杂度高于当前收益。后续以并行后的实际等待和机器时间再决定。

## 原因与代价

减少无关外部工作、夹具复制和串行等待，同时保留各个失败边界。CI 并行多启动一个 Windows runner 和一个很小的聚合 job，会增加启动/依赖准备与机器时间；收益以实测墙钟为准。固定宿主只在明确标记的测试生效，禁止整个套件全局 mock subprocess。离线成功仍不能认证真实成片或部署。

## 证据

- `test_selection_recovery.py`：重复窗口原断言、新旧实验适配器联动与最终组装。
- `tests/offline_host.py`：显式 opt-in 宿主事实；`test_resource_profile.py` 保留资源策略行为。
- `test_modular_architecture.py`、`test_bounded_frame_batch.py`、`test_acceptance_delivery_gate.py`：最小故障图、带音轨真实媒体、整任务收集后统一交付。
- `.github/workflows/ci.yml`、[测试策略](../test.md)、[发布流程](../release-process.md)。独立设计审阅采纳保留 main 全量的建议；当前 PR 的实际验证见 PR Checks。
